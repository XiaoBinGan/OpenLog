Why

手工运维的四个真实痛点

每一条都是我们自己踩过的，不是假设出来的场景。

01

日志散落

几十个容器、多台机器，出问题第一反应是 ssh 上去 grep。谁在报错、什么时候开始、影响哪些服务，全靠人肉拼。

→ 一次定位半小时起步，事后还答不出「什么时候开始」

02

算力黑盒

GPU 到底用没用上？模型 MFU 多少、是不是卡在显存或通信？只有 nvidia-smi 的一瞬间快照，没有连续视角。

→ 卡空转、显存泄漏，往往等业务报错才发现

03

救火式修复

定位到问题还得找机器、找文件、改配置、重启服务、再验证。一次故障十几分钟，全在切窗口。

→ 全靠人肉切窗口，改错一次要重来一遍

04

工具割裂

日志、监控、Docker、SSH 各用一套工具，上下文对不上；告警看完还得回去翻日志。

→ 一次告警要在 4 个工具之间来回跳

日志→发现异常→定位机器与容器→看算力与模型→让 AI 直接改代码 / 配置→验证与审计

Capability

六个真正「能动手」的能力

每个能力都能落到一次具体操作上，不只是给个图表看。

日志实时告警

采集 → 匹配 → 弹窗 → 跳转，一条链路闭环。

  • WebSocket 实时推送，多机器多容器并发流
  • 按级别、关键字、正则配置告警规则
  • ERROR 告警弹窗点一下直接跳到该容器日志

GPU 与 MFU

引擎无关的模型算力效率口径。

  • nvidia-smi 连续采样，保留趋势而非快照
  • MFU 支持 vLLM、SGLang 等 7 种引擎，零配置
  • 快照做瘦身，1000 台也不把库写爆

Docker over SSH

宿主机什么都不用装。

  • 远端 dockerode 桥接，等同本机 Docker API
  • 容器生命周期、实时日志、内嵌 PTY 终端
  • exec 能力做开关，生产可关可开

远程服务器

连接是基础设施，不是一次性动作。

  • 连接池 LRU + 空闲回收，限并发重连（默认 16）
  • 退避重连 5s → 10s → 20s → 5min，手动断开即停
  • 密码 AES-256-GCM 存储，支持密钥轮换

AI 运维助手（Agent）

看得见，也动得了手。

  • 多步工具调用：读文件、改代码、改配置、重启、验证
  • 用现有 SSH 账号执行，权限不隔离、全程审计
  • 排障过程沉淀为可复用技能

AI Shell 与模型兼容

自然语言 → 命令 → 结果 → 下一步。

  • 多步 Agent 循环，执行结果回灌给模型继续判断
  • OpenAI 兼容协议，vLLM / SGLang 都能直接接
  • 支持本地与内网模型服务（/v1 接口）

Architecture

分层架构：一层只做一件事

前端 React 18 + TS + Vite；后端 Node 22 ESM，单端口同时提供 API、WebSocket 与静态资源。

接入层
  • Express（ESM）+ WebSocket 统一入口
  • Token 鉴权门禁，生产环境 401 拦截
  • 单端口同时托管前端构建产物与 API
服务层
  • 路由域：logs / gpu / docker / remote / assistant / skills / db-info
  • 统一的错误包装、限流与审计埋点
  • 配置与状态走 kv，读写穿透内存缓存
能力层
  • 日志采集器 · 告警分发 · GPU 采样与 MFU 适配
  • SSH 连接池 · Docker 桥接 · 文件与 PTY
  • LLM 客户端与 Agent 工具编排（多步）
数据层
  • SQLite / PostgreSQL / MySQL 统一方言层
  • 同一份 DDL 与占位符转换，切换只改一个环境变量
  • 连接池 + 批量写，支撑 1000 台规模

Security

三道闸门，一把钥匙只开一扇门

AI 能改代码，所以审计比隔离更重要 —— 每个动作都要留痕、可回溯。

闸门 01

访问鉴权

全站 Token 门禁，未携带或错误直接 401；生产环境与开发环境开关分离。

闸门 02

凭据保护

服务器密码 AES-256-GCM 加密存储，支持 OPENLOG_SECRET_KEY 轮换；迁移链路已修复「二次加密」坑。

闸门 03

操作审计

AI 与运维助手的每一次命令、每一处文件改动都有记录；容器 exec 由环境变量显式开启。
